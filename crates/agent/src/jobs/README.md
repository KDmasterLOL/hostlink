# Agent command queue

The Agent owns an Apalis SQLite queue using upstream migrations only. Existing v5 databases are opened without HostLink schema scans or automatic migrations; missing jobs.db causes Agent startup to fail rather than create a replacement. Older jobs layouts are not imported or deleted. The optional board binds only to a nonzero loopback address; Tower HTTP validates the exact `Host` header before dispatch, while a small middleware checks `Origin`. All task lifecycle headers, priorities, schedules and retry limits are passed directly to the upstream Apalis Board API without HostLink policy overrides. `/new` submits a program and JSON argument array to the official board API. Commands do not invoke a shell implicitly. Anyone with local access to the board can run commands with the Agent's privileges.

`CommandJob` accepts an optional `timeout_seconds` between 1 and 14,400 seconds (four hours). Older task payloads and stored rows omit the field and retain the 900-second default; no database migration is needed. The existing loopback-only `GET /new` response advertises the supported maximum via `x-hostlink-command-timeout-max: 14400`; the Controller checks this read-only capability **before** submitting any command with an explicit timeout. Older Agents do not advertise the header and must be upgraded before using `--timeout-seconds`. Omitting the option still works with older Agents.

Shared owner-private filesystem and Windows DACL operations live in
`crates/agent/src/private_fs.rs` and the vendored `private-fs` crate. They are not an independent jobs store.

The service and updater do not query Apalis's Jobs table. On Linux and Windows the Agent supervisor holds an exclusive process-lifetime `jobs/runner.lock`; the updater requires the same canonical lock to be free before publication, while `update.lock` serializes concurrent updaters. Windows updates are **offline only**: explicitly stop and unregister the exact current-user Task Scheduler task before running a separate verified updater executable from outside installed `bin`. The updater refuses registered/running Agents; it does not use a control pipe, kill processes or restart services. Apalis retains pending and interrupted jobs; restarting a worker can replay commands and their side effects. See `docs/AGENT_UPDATE_WINDOWS.md` for the operator procedure and failure limits.

Apalis may replay work after a worker or Agent crash, including commands that already started; side effects can therefore occur more than once. The upstream API accepts an idempotency key for repeated submissions. Process execution requires a ProcessKit containment backend capable of tracking the process tree. Shutdown requests stop active process groups.
